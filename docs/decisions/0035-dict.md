# 0035. `dict` is Python's dict, with keys that compare exactly

Status: Accepted
Date: 2026-11-10
Roadmap: 1.13.4

## Context

Version 0 of the language has no `dict`. The [Types](../reference/types.md) chapter lists `list`,
tuples and arrays, and [Differences from Python](../reference/differences-from-python.md) names
`dict` displays among what Python has that version 0 does not. Roadmap 1.13.4 adds one.

Scientific programs need a map from a key to a value wherever data is labelled rather than
numbered: species name to mass, element symbol to Lennard-Jones parameters, `(i, j)` pair to a
bond constant, run setting to value, histogram bin to count. Without a `dict`, each of these is a
pair of parallel lists searched in a loop, which is slower and easier to get wrong.

The forces:

1. A Python reader should find a `dict` that reads and behaves like Python's, as every other
   collection does.
2. The language already has rules that a `dict` must fit: a value has one owner and moves
   ([Values and references](../reference/values-and-references.md)), a collection is borrowed for
   the whole of a loop over it, a bad index panics rather than raising
   ([Errors and panics](../reference/errors.md)), and `T | None` is checked before use.
3. Python allows any hashable key, floats included. A float key is a classic numerics bug:
   `0.1 + 0.2` is not `0.3`, so a lookup with a computed key misses, and `nan` is not equal to
   itself, so a `nan` key can be stored but never found again.
4. Results should be reproducible run to run, so iteration order must not depend on a random seed.

## Decision

**Python's `dict`, without float keys** (chosen by Collins on 2026-11-10).

### The type and its values

`dict[K, V]` maps keys of type `K` to values of type `V`. A display builds one, and an empty one
needs its type written, as an empty list does:

```python
masses = {"Ar": 39.948, "Ne": 20.180}
counts: dict[i64, i64] = {}
```

`K` may be:

- an integer type, `bool`, `str`, or an `Enum` without data;
- a tuple whose elements are all of those, such as `tuple[i64, i64]` for a pair of indices.

A float, a complex number, an array, a list, a `dict` or a struct as a key is a compile error that
says why. Floats are left out for the reasons in force 3; a program that needs to bin floats
converts them to an integer bin first, which says what "the same key" means. Structs as keys wait
for a trait that says how a struct hashes and compares, under
[decision 0031](0031-traits-are-protocols.md); until then a struct key is spelled as a tuple of its
fields. `V` may be any type.

A key literal takes the key type, as a number literal takes the other operand's type in number
mixing ([decision 0014](0014-number-conversions-are-calls.md)), so `counts[3]` on a
`dict[i32, i64]` looks up an `i32`.

### Operations

| Operation | Meaning |
| --- | --- |
| `d[k]` | The value for `k`. A missing key **panics**, naming the key, as an index out of range does |
| `d[k] = v` | Sets the value for `k`, adding `k` at the end of the order if it is new |
| `k in d`, `k not in d` | Whether `k` is a key |
| `len(d)` | The number of keys |
| `d.get(k)` | The value for `k` as a `V | None`: `None` when `k` is missing |
| `d.get(k, default)` | The value for `k`, or `default` when it is missing |
| `d.pop(k)` | Removes `k` and returns its value. A missing key panics |
| `d.pop(k, default)` | Removes `k` and returns its value, or returns `default` when it is missing |
| `d.copy()` | A new `dict` holding a copy of every key and value |
| `for k in d`, `d.keys()`, `d.values()`, `d.items()` | The keys, values, or `(key, value)` pairs, in insertion order |

A missing key panics instead of raising `KeyError` because looking up a key a program never put in
is the same kind of bug as reading past the end of an array, and the language already treats that
as a panic. A key that may be missing is a question the program asks out loud, with `in`, `get` or
`pop(k, default)`.

### Order

Iteration follows insertion order, as in Python since 3.7. Setting the value of a key that is
already present keeps its place; popping a key and setting it again moves it to the end. The order
never depends on a hash seed, so two runs of a program print their dictionaries the same way.

### Ownership

A `dict` owns its keys and values. It moves as a `list` does, and `copy()` is how to keep it and
pass it on. `d[k]` of a non-copy `V` is a read-only borrow, as a list element is, and a value is
moved out only by `pop`. A loop over a `dict` borrows it for the whole loop, so the body cannot add,
set or pop keys; Python raises `RuntimeError` for this at run time, and the exclusivity check
rejects it at compile time instead.

### Left for later

These are not part of version 0's `dict`, each for a stated reason, and each can be added later
without changing anything above: `del d[k]` (the language has no `del`; `pop` does the same job),
dict comprehensions (they wait for list comprehensions), `update`, `setdefault`, `|` and `|=`,
`fromkeys`, `popitem`, `clear`, `==` between dictionaries, and views that stay live after the
`dict` changes (`keys()`, `values()` and `items()` are only for loops).

### Building it

The runtime holds the table, as it holds list and string helpers today. The layout is CPython's
compact dict: a dense array of entries in insertion order and a separate open-addressing index of
small integers into it, so iteration is a walk over a contiguous array and the index stays small.
A popped entry leaves a hole that is skipped and reclaimed when the table next grows. The hash
function has a fixed seed, which force 4 asks for.

## Consequences

- Programs that label data get a structure that reads like Python and needs no parallel lists.
- Lookups, insertions and pops take constant time on average. A `dict` costs more memory than the
  same data in a list: the entries array, plus an index of one to eight bytes per slot, kept at
  most two-thirds full.
- Code ported from Python that uses float keys does not compile and must bin or round its keys.
  The error says so.
- Code that catches `KeyError` has nothing to catch; it is rewritten with `in`, `get` or
  `pop(k, default)`.
- A fixed hash seed means an adversary who controls the keys could make lookups slow by choosing
  colliding keys. Baryon programs compute on their own data, so reproducible order is worth more
  here than that defence; a service written in Baryon that takes keys from strangers is the case
  this leaves open.
- `dict` is the first collection whose element type is restricted. The restriction lives in one
  checker rule, so allowing struct keys later, once a hashing trait exists, changes that rule and
  nothing else.
