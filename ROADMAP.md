# Roadmap

This file is the single source of truth for what is planned, in progress and done. Every
contributor, human or AI agent, updates it when they start work and when they finish. New ideas
are welcome at any time: add them to [Ideas](#ideas).

The phases and work packages come from the [design plan](docs/design/language-design-plan.md),
which explains the reasoning behind each one.

## How to use it

1. **Before you start**, find the item you will work on, or add one. Set its status to
   `In progress` and put your name in Owner. Open a draft pull request early and put its link in
   Link, so others can see the claim.
2. **When you finish**, set the item to `Done` in the same pull request that completes it.
3. **If you are stuck**, set the item to `Blocked` and add the reason to its description.
4. **New ideas** go in the Ideas table with status `Idea`. An accepted idea becomes `Done`, linking
   the decision or pull request that accepted it, and its work moves into a phase as `Planned`
   items. A rejected idea becomes `Dropped` with a one-line reason.
5. **Never delete a row.** Finished and dropped items stay as the project's history.

`cargo xtask check-roadmap` keeps this file valid, and CI fails any pull request that changes
something without updating it. In every table, an empty cell is written `—`.

| Status | Meaning |
| --- | --- |
| `Idea` | Proposed; not yet accepted into a phase |
| `Planned` | Accepted and waiting for an owner |
| `In progress` | Someone is working on it; Owner says who |
| `Blocked` | Started, but waiting on something named in the description |
| `Done` | Finished and merged; Link points to the pull request |
| `Dropped` | Decided against; the description says why |

## Releases

A release is a tag on `main` that people outside the project can try, and
[`CHANGELOG.md`](CHANGELOG.md) says what each one holds. Releases are time-based (Collins,
2026-11-11): one every two weeks, cut from what `main` holds that day, so a release never waits for
a piece of work to finish. Each one is an item here with one row per step. The first is due on
2026-11-25 (R.5). Collins approves every release and pushes its tag himself.

The numbered efforts (R.2 for 0.2.0, R.3 for 0.3.0, R.4 for 0.4.0) are checkpoints, not release
gates. Each names a body of work and sets the order in which it is built; when one is finished,
work can pause there for testing, review and feedback. Whatever a checkpoint has merged ships in
the next time-based release.

Every release up to 1.0 puts working functionality for users first: a feature someone needs to
write, run or ship a real program comes before internal rework (Collins, 2026-11-10). Baryon
stands on its own: its libraries are written in Baryon and grow alongside it, so Python
interoperability comes in a later phase, after native language capability and native libraries,
never as a way to wrap Baryon in Python. A self-hosted compiler stays a non-goal, as the
[design plan](docs/design/language-design-plan.md) says.

After the 0.3.0 checkpoint, native capability comes before compile speed (Collins, 2026-11-10): speed of the
compiled code (3.1, 3.2, 3.3), then broadcasting and axis reductions (3.9), linear algebra and FFT
(3.10), statistics (3.16), file formats (3.14), DataFrame (3.13) and plotting (3.15). The base
libraries AstroPy relies on join them as Baryon's own (3.18 to 3.32): special functions,
integration, optimization, interpolation, spatial search and image processing, distributions,
missing values, record and date arrays, regular expressions, compression, XML, structured text,
networking, ERFA and world coordinate systems; ERFA (3.31) can start early, since it needs little
beyond what builds today. AstroBaryon, the native astronomy library (4.2), builds on them
(Collins, 2026-11-10). Phase 2's faster compiling follows, unless compile times start to slow
users down first. Python interop (3.17) comes only after as many native libraries as can be
built: Baryon should be a native language before it needs wrappers from other languages
(Collins, 2026-11-10).
